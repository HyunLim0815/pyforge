FAIR

PyForge PRD 在产品定位和边界定义方面表现出色——"uv 管依赖，PyForge 管项目"的 thesis 贯穿全文，竞品分析扎实，CLI 接口设计完整。但 PRD 在可测试性和决策透明度方面存在结构性缺口：FR 缺乏验收标准（critical），没有 Open Questions 章节，Success Metrics 不验证核心 thesis。

Adversarial 评审还揭示了更深层的问题——没有考虑 uv 自身可能填补这个空白、索引文件的竞态条件、以及 Python 项目识别标准的缺失。PRD 足以进入架构设计，但在投入开发前必须补上 FR 级别的验收标准。

Decision-readiness

ADEQUATE

PRD 在定位决策上非常果断：第 9 节的"PyForge 明确不做"是清晰的 negative space 声明，第 1 节的竞品分析有数据支撑。优先级（P0/P1/P2）是显式的开发排序信号。

但决策背后看不到权衡的痕迹：Web 框架的选择（"tiny_http 或 axum"）暴露了未完成的架构决策；Python 版本检测机制未定义；没有 Open Questions 章节——v1 产品不可能没有任何未决问题。

HIGH

没有 Open Questions 章节

全文
PRD 没有任何"未决问题"的集中表达。这隐藏了决策中的张力，让读者无法判断哪些是确定的、哪些是待定的。
Fix: 增加 Open Questions 章节，标记每项未决决策、Owner 和截止时间。
MEDIUM

技术选择仅有"或"无结论

§7.1
"tiny_http 或 axum" 暴露了架构决策未完成。
Fix: 二选一并说明理由，或将此明确列为 Open Question。
MEDIUM

Python 版本检测机制未定义

§8.1
展示了 python_version 字段但未说明如何获取。
Fix: 明确扫描策略（解析 pyproject.toml → 回退 python --version）。

Substance over theater

STRONG

PRD 几乎没有"填充物"：6 个用户角色各具差异化场景，无冗余。竞争分析基于真实空白，定位原创性真实可信。Vision 语句具体且不可迁移到其他产品。

NFR 大部分有具体阈值（1000 目录 < 3s，< 8MB），但"安全性"和"可扩展性"缺乏产品特定的量化指标。

LOW

NFR 中部分条目缺少阈值

§10
"安全性"和"可扩展性"两项只有定性描述，没有量化指标。
Fix: 补充具体约束，如"仅接受本地请求，无认证要求"等。

Strategic coherence

ADEQUATE

核心 thesis 明确：uv 管依赖，PyForge 管项目。特征演进（track → scan → info → new → web → 协作）遵循了自然顺序。

但 Success Metrics 不直接验证 thesis——下载量、Star 数、扫描速度是活动指标，而非 thesis 有效性指标。没有 counter-metrics 承认"又多了一个工具要学"的真实成本。

HIGH

Success Metrics 不验证核心 thesis

§13
指标测的是"多少人用了"而非"用得好不好"。
Fix: 增加产品价值指标，如"周活跃用户平均查看项目数"。
MEDIUM

没有 counter-metrics

§9, §13
"又多了一个要学的工具"是真实成本，未被承认。
Fix: 增加"学习成本"或"初次设置时间"作为负面指标。

Done-ness clarity

THIN

这是 PRD 最薄弱的维度。F1-F37 全部是功能意图描述而非可验收的功能定义。没有一个 FR 包含"给定 X，执行 Y，应得到 Z"的验收条件。下游 Epics/Stories 无从知道"做完"的边界。

多处使用"详细信息""概览""分布"等未量化的名词。Web API 端点（§7.3）较好，但 /api/open（POST）的参数结构未定义。

CRITICAL

几乎所有 FR 缺少验收标准

§3
F1-F37 没有包含任何可验证的验收条件。下游无从知道"做完"的边界。
Fix: 为每个 P0 FR 补充 1-2 个 Acceptance Criteria。
HIGH

模糊表述多处出现

§3 (F4, F18, F21)
"详细信息""概览""分布"等未量化的名词。
Fix: 对每个模糊字段给出具体字段列表。
HIGH

"复用 uv"缺乏集成定义

§9
多处提到"调用 uv init""复用 uv"，但没有定义调用路径。
Fix: 明确集成策略：采用 CLI 子进程调用 + 解析 stdout/stderr。

Scope honesty

ADEQUATE

§9 的"PyForge 明确不做"是教科书级的 negative space。优先级系统诚实地区分 P0/P1/P2。版本规划（§12）清晰定义了各版本的范围。

但 PRD 没有任何 `[ASSUMPTION]` 或 `[NON-GOAL for MVP]` 标注，也没有 Open Questions 章节。

MEDIUM

无假设标注

§3, §6
多处未验证的推断（如社区会贡献语言包）没有标记为假设。
Fix: 添加 [ASSUMPTION: ...] 标注并建立 Assumptions Index。
LOW

无 MVP 范围标记

§3
FR 级别没有 [NON-GOAL for MVP] 标记。
Fix: 在 P1/P2 功能后添加标注以减少歧义。

Downstream usability

ADEQUATE

PRD 结构清晰、目录完整，每个章节可独立阅读。F 编号连续（F1-F37），跨章节引用一致。

主要不足：没有 Glossary——"脚手架""子包""跟踪"等术语从未正式定义。用户故事没有正式 UJ 编号，无法在 FR 中精确引用。

MEDIUM

缺少 Glossary

全文
关键术语"子包""脚手架""跟踪"未定义，下游可产生歧义。
Fix: 增加 Glossary 章节，定义所有领域名词。
LOW

用户故事无正式 ID

§11
8 个故事使用无序数字列表，无法在 FR 或架构讨论中精确引用。
Fix: 为每个用户故事分配 UJ1-UJ8 ID。

Shape fit

STRONG

PyForge 是开发者工具（CLI + Web），采用能力规格（capability spec）形态非常合适——特征表格为主、用户故事为辅助示例。没有过度形式化，用户故事数量合理。

Adversarial review

review-adversarial.md

敌对性评审揭示了 PRD 作者可能回避的深层问题：竞争格局动态性（uv 可能进入同一领域）、文件系统并发安全、以及"Python 项目"这一基础概念的模糊性。这些问题是架构设计前必须解决的。

CRITICAL

没有考虑 uv 的竞争反应

§1, §9
PRD 假设 uv 永远只做依赖管理。uv 已发展成生态系统，完全可能在一年内增加项目索引功能。
Fix: 明确差异化策略或承认此风险。
HIGH

索引文件的竞态条件和数据一致性问题

§7, §8
projects.json 可能被多个终端会话同时修改。
Fix: 使用文件锁或 SQLite。
HIGH

没有定义"Python 项目"的识别标准

§3.1 F3
scan 命令依赖一个隐含分类器，边缘情况未处理。
Fix: 明确定义识别规则层级。
HIGH

Web 看板是过度的分布式架构

§3.5, §7
启动 HTTP 服务器远比 pyforge list 重。
Fix: 将 Web 看板降级为 P2。
MEDIUM

i18n 的优先级过高

§3.7, §6
7 个 FR 分配给 i18n 且标记为 P1，而核心功能仍在 P1/P2。
Fix: 将完整 i18n 框架降到 v1.1+。
MEDIUM

没有离线/降级策略

§3, §7
模板获取方式、索引恢复流程等未定义。
Fix: 明确联网需求，确定模板分发策略。
LOW

没有 Shell 补全的设计

§4
开发者工具的 CLI 缺少 bash/zsh/fish 补全。
Fix: 在 CLI 设计阶段加入 Shell 补全支持。
LOW

SKILL.md 分发机制假设过多

附录 B
自动写入 AI 工具配置属于侵入性操作。
Fix: 改为安装时提示 + pyforge init-agent 手动命令。

Mechanical notes

  • F-ID 连续（F1-F37），无断号或重复
  • 没有 Glossary 定义关键术语
  • 没有 Assumptions Index
  • 用户故事有角色名但无正式 UJ 编号
  • 目录完整、跨章节引用一致
